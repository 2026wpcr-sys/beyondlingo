## Question

翻译层走云端 LLM 还是端侧模型？这决定「完全离线」这个目标是否成立。

## Answer（2026-11-12 用户拍板）

**选 A：纯混合方案。**

- **ASR 离线**（sherpa-onnx 流式 Zipformer + SenseVoice 重打分）
- **TTS 离线**（Matcha zh-en；日/韩用系统 TTS 兜底）
- **翻译走云端 LLM**（复用 beyondlingo 现有引擎：Yandex 直连 / 自定义 LLM 如 glm-4-flash）
- **不引入 ML Kit 端侧翻译**，不做离线模式切换

### 由此确定的约束

1. **隐私定位**：音频全程不出设备；只有识别出的文字外发。这是相对翻译鸥（音频→火山引擎）、变色龙（音频→火山引擎）的实质优势，应作为产品卖点写进 UI。
2. **UI 必须明确提示「翻译需联网」**，不能让人误以为全离线。
3. **不需要语言包下载/管理模式** —— 省掉一整套下载、校验、版本管理、存储配额的工程。
4. **APK 体积压力集中在 ASR/TTS 模型**（中英 ≈198MB + Matcha ≈93MB），仍需「首装内置中英，其余按需下载」策略。
5. 断网时翻译失败要降级为「仅显示原文」，不能整条同传崩掉（见 Not yet specified）。

### 被否掉的方案

- **B 全离线**：ML Kit 约 30MB/语言对，中英日韩互译体积膨胀严重，且长段落译文质量明显下降。
- **C 全云端**：音频也上云，隐私最差且持续产生 API 费用。
